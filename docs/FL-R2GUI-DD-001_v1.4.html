SkyFolder
Cloudflare R2 × macOS Finder マウント＆共有 GUI 詳細設計書

SkyFolder は、接続情報をアプリ画面に入力するだけで任意の R2 バケットを Finder にマウントし、 マウント済みファイルから恒久公開 URL・期限付き共有 URL をワンクリックで発行できる macOS ネイティブ GUI アプリケーションの詳細設計。 FL-R2FS-DD-001 v1.4（CLI 版・単一構成固定）が確立した技術基盤を継承しつつ、 設定の汎用化と操作面の GUI 化という 2 点でスコープを拡張する。

§00 結論（TL;DR）

  1. GUI スタックは SwiftUI ネイティブ（G-01）。 本ツールの価値の中心は「Finder にマウントされること」で、これは macOS 固有機能である。クロスプラットフォーム framework の利点が原理的に発生しない一方、MenuBarExtra・Keychain・NSWorkspace・UserNotifications がファーストパーティ API として使えるため、常駐型メニューバーアプリとして最短距離になる。
  2. rclone は「その都度 spawn」ではなく rclone rcd を常駐させ HTTP RC API で制御する（G-02）。 mount/mount mount/unmount mount/listmounts operations/publiclink core/stats vfs/stats が公式 API として揃っており、マウント制御・共有 URL 発行・転送進捗表示が単一の口で完結する。GUI が「今どうなっているか」を常時握れることが CLI 版との決定的な差になる。
  3. macOS では mountType: "nfsmount" の明示が必須（G-03 / CRIT-01）。 実測した mount/types の応答は ["cmount", "nfsmount"] で、mount(FUSE) は登録されていない。したがって省略すると cmount が選ばれ、macFUSE 未導入の環境では失敗する。nfsmount が rc に登録されていることはソース（mountlib.AddRc("nfsmount", mount)）と実測の両方で確認済み。
  4. 設定は「プロファイル」単位で汎用化する（G-04）。 DD-001 が固定値としていたバケット名・公開ドメイン・マウントパス・ラベルを、すべてユーザー入力項目へ昇格させる。非機密は JSON（0600）、Access Key ID / Secret Access Key は Keychain に保存し、rcd へは環境変数で注入して rclone.conf に平文の secret を書かないことを原則とする。
  5. 共有は 2 系統をボタン化する（G-05）。 恒久公開 = public バケット + カスタムドメインで {publicBaseURL}/{key} を組み立て、期限付き = operations/publiclink（expire 付き）で presigned URL を発行。いずれもクリップボードへ即コピー。DD-001 §8 の r2share CLI がそのまま GUI のボタンに写像される。
  6. public バケットは read-only でマウントする（G-08）。 DD-001 が最大の運用リスクとした「Finder で public へ直置きすると Exif 除去が働かない」を、検知や警告ではなく書込みを構造的に不可能にすることで消す。公開は必ず共有ダイアログを通るため、slug 化・上書き確認・メタデータ除去を迂回できない。Exif 除去自体は ImageIO でアプリ内実装し、外部 exiftool に依存しない（G-06 / SEC-G03）。
  7. 配布は Developer ID 署名 + notarization の .app。App Sandbox は無効（G-07）。 子プロセス実行・任意パスへのマウント・localhost NFS は App Sandbox と両立しないため、Mac App Store 配布は構造的に不可能。この判断は将来も覆らない。
  8. 主要な技術前提は実測で確定済み（v1.2）。 rclone v1.75.0 を macOS 26.6.2 で実際に動かし、RC API を叩いて 環境変数のみでのリモート定義（U-01）・per-mount の read-only（U-12・G-08 の実現機構）・mount/mount の同期性（U-11）・_filter の持続（U-08）・vfsOpt の数値形式（U-02）の成立を確認した。 一方で Cache-Control の実付与（U-04）と presigned URL の実発行（U-13）は、検証に使った type=local では原理的に確認できず未検証のままであり、G1-9 で実 R2 アカウントを使って確かめる。 あわせて本書の記述の誤りを発見・修正している（mountTypes に mount は存在せず省略時は cmount が選ばれる）。詳細は §14.1。
  9. v1.4 — 実装したところ、なお 13 件の差分が出た（M-12〜M-22）。 本書は 2 モデルの独立レビューと実機検証を経て v1.3 に達し、両レビュアーが APPROVE を出していたが、 実際にコードを書いて動かすと 4 件は記述どおりに実装すると止まるか無言で壊れるものだった: (M-12) --log-file を付けるとポートは stdout にも stderr にも出ない（v1.2 の訂正は不十分だった）／ (M-13) operations/uploadfile は _async で jobid を返さず、G4 の AC が成立しない／ (T-G30) 「同梱バイナリを個別署名する」（G0-3）と「ハッシュが記録と一致する」は両立しない／ (M-15) ImageIO の除去は kCFNull を明示しないと効かず、SEC-08（MUST）が無言で壊れる。
    設計レビューは実装の代わりにならない。 該当箇所は本文で訂正済み。全件は §14.1 の M-12〜M-22 と docs/IMPLEMENTATION-NOTES.md。
  10. 冪等性は「望む終了状態」に対して設計する（§8.6・実測に基づく）。 実測の結果、mount/unmountall と options/set は冪等だが、 mount/mount（already mounted）と mount/unmount（mount not found）はエラーを返すため、これらは成功として扱う。 さらに rcd は --rc-addr 127.0.0.1:0 だと二重起動しても別ポートで両方立ち上がる（CRIT-03）ため、 プロセスの単一性はアプリが PID ファイルと単一インスタンス化で担保しなければならない。
  11. ロードマップは 6 フェーズ・正味 6〜8 日相当: G0 プロジェクト基盤 → G1 rcd 制御層 → G2 プロファイル/Keychain → G3 マウント UI → G4 共有 UI → G5 診断・配布。 v1.2 の実機検証により G1 の役割は「検証」から「実装 + 実 R2 アカウントでの通し確認」に変わり、2 日へ短縮した。 ただし G1-9（実アカウントでの通し確認）は省略してはならない — SigV4 署名・マルチパート・presigned の実発行（U-13）・Cache-Control の実付与（U-04）は、まだ一度も成功させたことがない。

01. 目的・スコープ・利用者像

1.1 目的

  • 接続の民主化。 DD-001 の CLI 手順（rclone.conf 手書き・launchd plist 配置・zsh スクリプト作成）を、アプリ画面へのフォーム入力 1 回に置き換える。ターミナルを開かずに R2 を Finder のドライブにできることを完成状態とする。
  • 汎用化。 DD-001 が fracturelab.dev 専用の固定構成だったのに対し、本アプリは任意の Cloudflare アカウント・任意のバケット・任意の公開ドメインを受け付ける。設定はプロファイルとして複数保持でき、切り替えられる。
  • 共有の即時化。 マウント済みファイルを選択して 1 アクションで、恒久公開 URL または期限付き共有 URL を発行しクリップボードへ入れる。「URL を出して人に渡す」までの所要を 10 秒以内に収める。
  • 状態の可視化。 CLI 版では見えなかった「今マウントされているか」「未アップロードのキャッシュが残っているか」「転送中か」をメニューバーから常時確認できるようにする。DD-001 R-03（保存 ≠ 即クラウド同期）が引き起こす不安を、UI で解消する。

3.7 G-08: public バケットのマウント → read-only でマウントする

DECISION — 最重要リスクを、検知ではなく構造で消す

DD-001 §0.5 が最大の運用リスクとした「Finder で public へ直置きすると Exif 除去が働かない」は、 public バケットを読み書き可能でマウントしているからこそ発生する。 書込みを構造的に不可能にすれば、この経路は検知するまでもなく存在しなくなる。

案評価判定
public は read-only
でマウント		 vfsOpt に "ReadOnly": true を指定する（visibility == "public" のバケットにのみ適用）。
利点: (a) Finder 直置きによる Exif 未除去公開が原理的に発生しない — CRIT-02 の検知機構（FSEvents）も U-07 の不確実性も丸ごと不要になる。 (b) 公開バケットの誤削除・誤上書きも同時に防げる。 (c) 「公開は必ず共有ダイアログを通る」という単一経路が強制され、slug 化・上書き確認・メタデータ除去が迂回できなくなる。 (d) 実装量が減る（G4-6 が不要になる）。
代償: Finder から public のファイルを直接削除・リネームできない。これらはアプリの「公開物一覧」（§5.4）から行う。 公開物の管理は元々 gone/ 移動という特殊な運用（DD-001 §4.4 の URL 不変性）を要するため、むしろアプリ経由に限定するほうが正しい		 採用
read-write でマウントし
FSEvents で検知・是正		 Finder から直接操作できる自由度は高いが、本書で最も重大な残存リスクを抱え込んだうえ、その対策が未検証の前提（FSEvents が NFS 上で発火するか＝U-07）に依存する。 さらに検知はアップロード完了後に働くため、原本が公開される時間窓を原理的に消せない。 自由度と引き換えに負う代償として釣り合わない 不採用
public をマウントしない リスクは最小だが、公開済みファイルを Finder で閲覧・プレビューできなくなり、「Finder にマウントする」という本ツールの中心価値が半減する 不採用
NOTE — この決定が本書に及ぼす影響
  • CRIT-02（FSEvents による検知）は v1.0 では実装しない。 read-only マウントにより対象の経路が存在しないため
  • U-07（FSEvents が NFS 上で発火するか）は v1.0 のブロッカーから外れる。 参考情報として残す
  • G4-6（検知の実装）はロードマップから削除し、代わりに「public が read-only でマウントされていることの検証」を置く
  • ユーザーが意図的に public へ直接書きたい場合のため、詳細設定に allowDirectWriteToPublic（既定 false）を用意する。true にすると read-write でマウントされ、その旨の警告が設定画面とメイン画面に常時表示される。この設定を有効にした場合のみ、Exif 未除去公開のリスクを利用者が引き受けたものとして扱う。
    反映タイミング: この設定の変更は即座に該当バケットを再マウントして反映する（アンマウント → 設定変更 → 再マウント）。手動再マウントを待つ実装にしてはならない — 「設定したのに反映されていない」状態が生まれ、ユーザーが read-only だと誤認したまま書込みを試みることになるため
  • この決定は実測で成立を確認済み（U-12）。 同一 rcd から 2 箇所にマウントし、ReadOnly: true 側だけが書込み・削除を拒否することを確認した（rclone v1.75.0 / macOS 26.6.2）
  • ただし OS レベルでは read-only ボリュームにならない（M-01）。 mount の出力に read-only フラグは付かず、拒否は rclone の VFS 層で行われる。 つまり Finder は「書ける」と認識してドラッグ&ドロップを許可し、そのあとで失敗する。 「Finder が事前に止めてくれる」ことを期待した設計にしてはならず、§5.2 の「読み取り専用」バッジと E-14 の案内が必須になる。 安全性（Exif 除去の迂回を防ぐ）は達成されるが、操作を試みたユーザーには失敗が起きるという UX 上の代償を伴う

6.1 rcd の起動

RcdSupervisor が組み立てる起動コマンド（概念形）

{app}/Contents/Resources/rclone rcd \
  --rc-addr 127.0.0.1:0 \            // 0 = 空きポート自動割当。固定ポートを使わない

  // --config は必ず空文字。設定ファイルは生成しない（U-01 が実測で成立済み）

RCLONE_RC_PASS={random 32 chars}          // 同上

// リモート定義（G-04 第 1 案。§14.1 U-01 で実機検証）
RCLONE_CONFIG_R2_TYPE=s3

RCLONE_CONFIG_R2_SECRET_ACCESS_KEY={keychain}

RCLONE_CONFIG_R2_ACL=private
RCLONE_CONFIG_R2_NO_CHECK_BUCKET=true   // DD-001 §6.2: バケット作成権限がないトークンで必須

// K-02（NFC 正規化）: rclone の --no-unicode-normalization は既定 false のまま維持する。
// 環境変数でもフラグでも変更しない。アプリの設定項目としても提供しない。
// macOS は NFD を返すことがあり、正規化を切ると同名別ファイルが発生する（DD-001 K-02）

// グローバル / バックエンドのオプション（mount/mount では渡せない項目。§6.2 注入経路表）
RCLONE_TRANSFERS={advanced.transfers}                       // 既定 8

RCLONE_S3_UPLOAD_CUTOFF={advanced.s3UploadCutoffMB}M        // 既定 128M
// nfs-cache-handle-limit は環境変数で渡さない。既定値が既に 1000000 で
// DD-001 §6.3 の指定値と一致する（実測・U-09）。明示したい場合は起動後に
// options/set へ {"nfs":{"HandleLimit":1000000}} を送る
MUST — rc API はシェルアクセスと等価

rclone 公式が「API へのアクセスはシェルアクセスと同等」と明記している。したがって: (a) --rc-no-auth を使ってはならない、 (b) バインドアドレスは 127.0.0.1 に限定し 0.0.0.0 にしてはならない、 (c) rc-user / rc-pass はプロセス起動ごとの乱数とし、ディスクに書いてはならない。 ポートを固定しない（:0 で自動割当）のは、同一マシンの他プロセスが待ち構えることを困難にするためでもある。 割り当てられた実ポートは --log-file が指すログファイルから読み取る — 実測では NOTICE: Serving remote control on http://127.0.0.1:63283/ の形式で出力される。 v1.3 まで「stdout ではなく stderr に出る」としていたのは誤りだった（M-12）。 それは --log-file を付けずに測った結果で、本節が必須としている --log-file を指定すると stdout も stderr も 0 バイトになる。stdout を読んでも stderr を読んでも永久に待ち続ける。 ログファイルは再起動をまたいで追記されるため、起動前のファイルサイズを記録し、そこから後ろだけを走査すること — さもないと前回起動時の古いポートを掴む（CRIT-03 と同種の事故）。

CAUTION — 環境変数はプロセス一覧から見えない、が漏れうる

環境変数は ps のコマンドライン引数と違って一覧に出ないが、同一ユーザー権限のプロセスからは /proc 相当の手段や親プロセス経由で読める場合がある。 これは Keychain 保存に比べれば弱い保護であり、「ディスクに平文で残らない」ことが主たる利益である点を正しく理解して実装すること。 secret を --rc-* 等のコマンドライン引数に置くことは、いかなる場合も禁止する（引数は ps で全ユーザーから見える）。

8.6 冪等性の設計（実測に基づく）

DD-001 §6.2 は「rclone config の対話は使わず設定ファイルを直接配置する（冪等・再現可能にするため）」と、冪等性を明示的な設計目標に掲げていた。 GUI では同じ操作がユーザーの手で何度も繰り返される（ボタンの二度押し、自動再マウントとユーザー操作の競合、クラッシュ後の再起動）ため、 この要求は CLI 版より強くなる。本節は rclone v1.75.0 での実測に基づき、どの操作が冪等でどれが冪等でないかを確定させる。

PRINCIPLE — 「操作」ではなく「望む終了状態」に対して冪等にする

本アプリのすべての状態遷移は宣言的に書く。「マウントする」ではなく「マウントされている状態にする」、 「アンマウントする」ではなく「マウントされていない状態にする」を実装の単位とする。
したがって「すでにその状態である」ことを示すエラーは、失敗ではなく成功として扱う。 これを守らないと、ボタンの二度押し・自動再マウントとの競合・再起動直後の操作が、すべてエラーダイアログになる。

8.6.2 rcd プロセスの単一性（最重要）

CRIT-03 — rcd の重複起動は rclone が防いでくれない

実測: --rc-addr 127.0.0.1:61999 のようにポートを固定した場合、2 本目は CRITICAL: Failed to start remote control: failed to init server: listen tcp 127.0.0.1:61999: bind: address already in use で失敗する。 しかし本アプリが採用する --rc-addr 127.0.0.1:0（空きポート自動割当・§6.1）では、2 本目は別のポートを取得して両方とも起動してしまう（実測: 61987 と 62097 で同時に稼働）。
すなわち rcd プロセスの単一性は、rclone ではなくアプリが担保しなければならない。

起こりうる事故（実際に再現済み）: アプリの異常終了で rcd が孤児として残ったまま再起動すると、 2 本の rcd が同じマウントポイントを奪い合う。
実測: 旧 rcd（ポート 61662）がマウントを持ったまま新 rcd（ポート 61697）を起動したところ、 新 rcd から見た mount/listmounts は 0 件を返した。 しかし OS 上には当該マウントが 1 件実在していた（mount コマンドで確認）。
すなわち §02 の DESIGN INVARIANT「マウント状態の真実は listmounts の応答である」が、この状況では嘘になる。 アプリは「マウントされていない」と表示し、ユーザーは Finder で見えているドライブとの矛盾に直面する。

実装（MUST・§8.1 の手順 0 として実施）:

  • (a) PID ファイルを持つ: ~/Library/Application Support/dev.fracturelab.skyfolder/rcd.pid に、起動した rcd の PID と割り当てられたポートを書く
  • (b) 起動時に前回の残骸を回収する: PID ファイルが存在したら、その PID のプロセスが実在し、かつ自分が起動した rclone であることを確認する （PID の使い回しを踏まないため、proc_pidpath で実行パスを取得し同梱バイナリと一致するかを見る）。 確認できたら SIGTERM → 5 秒待って SIGKILL で終了させる。
    孤児に対して RC API を呼んではならない（実装不能）: rc-user / rc-pass はメモリのみで永続化しない（§4.1 / SEC-G01）ため、 前回インスタンスの認証情報はすでに失われており、孤児の rc は 401 を返す（実測で確認済み）。 PID ファイルに認証情報を書けば呼べるようになるが、それは SEC-G01 自身に違反するため採らない。 SIGTERM で足りることは実測で確認済み（M-08） — マウント中の rcd に SIGTERM を送ると、 プロセス終了と同時にマウントが自動的に解除された（mount の出力から消えた）。RC API を呼ぶ必要はない。
    PID ファイルが無い孤児（書込み失敗・ユーザーによる手動削除）も回収できるよう、フォールバックとして 実行パスが同梱バイナリと一致する rclone プロセスを走査する（他のアプリや、ユーザーが自分で入れた rclone を巻き込まないため、パス一致を条件にする）
  • (c) アプリ自身の単一インスタンス化: macOS は通常 .app の二重起動を防ぐが、ターミナルから実行ファイルを直接叩けば回避できる。NSRunningApplication で同一 bundle identifier の先行インスタンスを検出し、存在すればそれを前面に出して自分は終了する
  • (d) 終了時に PID ファイルを削除する。異常終了で残った場合は (b) が回収する

この 4 つが揃って初めて「アプリを何度起動しても、rcd はつねに 1 本」という冪等性が成立する。 (b) を実装せずに (c) だけでは、アプリがクラッシュしたあとの孤児 rcd を回収できない。

VERIFIED — 回収手順を通しで実証済み（M-09）

上記 (b) の手順を実機で通し実行し、破綻の再現から解消までを確認した:

  1. rcd を起動してマウント → rcd.pid に PID とポートを記録
  2. rcd を残したまま「アプリだけ落ちた」状態を作る（孤児化）
  3. 回収せずに新 rcd を起動 → 破綻を再現（新 rcd の listmounts は 0 件、OS 上は 1 件）
  4. PID ファイルから PID を読み、ps -p {pid} -o comm= で実行パスが同梱バイナリと一致することを照合（PID 使い回しを踏まないため）
  5. SIGTERM を送出 → 1 秒で終了し、OS 上のマウントも 0 件になった（M-08 のとおり自動解除される）

結果: rcd 0 本 / マウント 0 件。回収手順は設計どおり機能する。 SIGKILL まで進むケースは今回発生しなかったが、その場合に備えた §8.4 手順 2 の例外規定は残す。

8.6.3 アプリ操作の冪等性

操作冪等にするための規定
起動シーケンス（§8.1）どの手順から中断・再開しても同じ終了状態に至ること。 手順 0（rcd 残骸の回収）→ 1〜8 を、前回どこで落ちたかを問わず毎回すべて実行する。「前回どこまで進んだか」を記録して途中から再開する実装をしてはならない（その記録自体が壊れうる）。
補足 — autoMount と手動アンマウントの関係: §8.2 は「Finder で手動アンマウントされたら自動再マウントしない」と規定しており、これには何らかの記憶が要る。 本原則と矛盾しないよう、次のとおり整理する: autoMount（永続設定）は起動時に一度だけ評価する。実行中に手動アンマウントされた事実はセッションスコープのメモリにのみ保持し、永続化しない。 したがって次回起動時は再び autoMount に従ってマウントされる（アンマウントしたまま覚えておく実装にはしない）
マウント（§6.2）§8.4 の stale mount 掃除 → mount/mount → already mounted は成功扱い。実行後に mount/listmounts で望む状態になったかを確認し、その結果のみを UI に反映する（§02 DESIGN INVARIANT）
プロファイル保存（§4.1）Keychain は SecItemUpdate→無ければ SecItemAdd の順（Add を先に呼ぶと重複エラーになる）。profiles.json は全体を書き直す（追記しない）。書き込みは一時ファイル + rename(2) の原子的置換とし、途中でクラッシュしても壊れた JSON が残らないようにする
プロファイル削除（SEC-G07）2 回目の削除では Keychain が errSecItemNotFound を返す。これは成功として扱う（目的は「その項目が存在しない状態」であり、すでにそうなら達成されている）。
profiles.json からの除去は保存と同じく全体を書き直し + 一時ファイル → rename(2) の原子的置換。
削除対象が activeProfileId だった場合の付け替え規則: 残ったプロファイルのうち先頭のものを新しい active にする。1 つも残らない場合は activeProfileId を空にし、オンボーディング画面へ戻す（起動時に §8.1 の手順 2 が失敗して停止するのを避けるため）
期限付きリンクの発行（§7.2）本質的に非冪等 — 呼ぶたびに新しい署名と期限を持つ URL が返る。ただし状態を壊さない（署名はローカル計算で、既存の URL を無効化しない）ため、再実行を妨げる必要はない。クリップボードを失った場合の再発行が安全なのはこの性質による（§7.2 の「再コピー」）
接続テスト（§4.4）プローブのキー名に乱数を含める（すでに §4.4 手順 5 で規定）。前回のプローブが後片付け前に落ちて残っていても、次回のテストと衝突しない。起動時に .skyfolder-probe-* を掃除する（見つかっても失敗扱いにしない）
恒久公開（§7.3 の 6 手順）手順 3 の Exif 除去は一時ディレクトリの複製に対して行い、原本を変更しないため、何度実行しても入力は同じ。手順 2 の衝突確認 → 上書き確認は毎回行う。
途中で失敗した場合、一時ディレクトリを削除してから終了する（defer 相当の確実な後始末）。同じファイルを再度公開すれば同じ key・同じ URL になる（slug 規則が決定的であるため）
取り下げ（§5.4）v1.3 まで「movefile が失敗しうる」としていたのは実測と逆だった（M-14）。operations/movefile は移動先が既に存在してもエラーにならず黙って上書きする。

帰結: 孤児 rcd の回収（§8.6.2 (b)）で mount/unmountall を呼ぶ必要がない。 これは重要で、孤児の rc-user / rc-pass は失われているため RC API は 401 になり呼べない（SEC-G01 が認証情報を永続化しないため）。 SIGTERM だけで完結するという事実が、「認証情報を永続化しない」という原則と「孤児を回収する」という要求を両立させている。

M-05 環境変数で定義したリモートは config/dump に現れない config/dump の応答は空オブジェクトになる（環境変数由来の設定は config ファイルの内容ではないため）。これは異常ではない。

15.1 プロダクト名と、名前の階層

MUST — リポジトリ名と bundle identifier を連動させない

  • Application Support / Caches / Logs のディレクトリが変わり、プロファイル設定を見失う
  • Developer ID 署名の連続性が切れ、ユーザーには「別のアプリ」として見える

A-04 の実測（M-10）がここにも効く: メニューバーは 16〜18pt であり、現物の線画をそのまま縮めると潰れて判別できない。 A-04 の 16pt 用別版と同じデータを流用できるよう、両者をまとめて設計すること（フォルダの輪郭のみに絞る、線幅を 2〜3 倍にする等）
A-07 DMG の背景画像
（G5・任意）		 ロゴを流用できるが、DMG は Retina 用に @2x も要る。優先度は低く、無くても配布は成立する
DECISION — アセット作業は G0 に置く

A-01〜A-06 は G0（プロジェクト基盤）で実施する。理由は、 アイコンが無いとビルドしたアプリの見た目が Xcode の既定のままになり、以降の全フェーズで「仮の姿」を見続けることになるため。 特に A-06（メニューバーアイコン）は G3 の常駐 UI で必ず要るので、後回しにすると G3 が止まる。
ただし A-01 の「元データを用意し直す」判断だけは人間の作業であり、暫定の拡大版で G1〜G4 を進めることは許容する（G5 までに差し替える）。
