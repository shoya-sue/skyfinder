> 本ファイルは「なぜそう直したか」の詳細と、実測の生データを残すためのもの。

実装日: 2026-08-31 / 環境: macOS 26.6.2 (25G83) arm64 / Xcode 26.6 / Swift 6.3.3 / rclone v1.75.0

設計書は **2 モデルの独立レビューと実機検証を経て v1.3** に達していたが、
実際にコードを書いて動かすと、なお **17 件**の差分が出た。

## A. 設計書の記述どおりに実装すると止まる・壊れるもの

### M-12 — rcd の待受ポートは stderr ではなく**ログファイル**に出る

**該当**: §8.1 手順 4 / §6.1 MUST / U-05 / T-G02

設計書は「ポートは stdout ではなく **stderr** に出る。stdout を読む実装にすると永久に待つ」と、
v1.2 で誤りを 1 度訂正している。しかしこれは **`--log-file` を指定しないで測った結果**だった。

§6.1 が必須としている `--log-file` を付けると、実測は次のとおり:

| 出力先 | 内容 |
|---|---|
| stdout | **0 バイト** |
| stderr | **0 バイト** |
| ログファイル | `NOTICE: Serving remote control on http://127.0.0.1:54681/` |

**stderr を読む実装も永久に待つ。** 設計書の訂正は不十分だった。

**実装**: `RcdPortReader` がログファイルから読む。
ログは再起動をまたいで追記されるため、**起動前のファイルサイズを記録し、そこから後ろだけを走査する**
— これをしないと前回起動時の古いポートを掴む（CRIT-03 と同種の事故になる）。
stderr も保険として拾うが、実測では空。

### M-13 — `operations/uploadfile` は `_async` を受け付けない（jobid を返さない）

**該当**: §7.3 手順 4 / §6.5 / G4 の AC

設計書 §7.3 手順 4 は恒久公開のアップロードを
`operations/uploadfile（_async: true）` と規定し、G4 の AC は
「URL のクリップボードコピーは、アップロードジョブの完了（`job/status` が成功）を待ってから行う」としている。

実測: `operations/uploadfile` は **multipart/form-data** で、
`_async` を form field で渡しても **jobid を返さず同期実行**される（応答は `{}`）。
`job/status` でポーリングする経路が存在しないため、**進捗表示が原理的に作れない**。

対して `operations/copyfile` は:

| 項目 | 実測 |
|---|---|
| `_async: true` | `{"executeId": "...", "jobid": 1}` を返す |
| `job/status` | `{finished, success, error, duration}` が取れる |
| `_config.UploadHeaders` | 受理される（U-04 の形式確認と同じ） |

**実装**: アップロードは `operations/copyfile` を使う。
そのためにローカル側にも名前付きリモートが要るので、`RCLONE_CONFIG_LOCAL_TYPE=local` を
環境変数に追加した（秘密情報を含まないので SEC-G01/G02 に影響しない）。

### T-G30 の自己矛盾 — 署名すると同梱 rclone のハッシュは必ず変わる

**該当**: G0-3 / §9.2 NOTE / §10.2 / T-G30

- **G0-3**: 「ネストされた実行可能ファイルとして個別署名する」
- **T-G30**: 「診断画面の同梱 rclone のバージョンと SHA-256 が `docs/BUNDLED.md` の記録と一致する」

この 2 つは**両立しない**。実測:

| | SHA-256 |
|---|---|
| 配布物（署名前） | `f52ccc22e6fe61ea5791f0e186db323155ad1cc1b6dfe547f4bc665bea57a2dd` ← BUNDLED.md と一致 |
| `.app` 内（署名後） | `dcb481860f6597451e9a535023287ef8c0ba049368034784521401ace6fb3c76` |

**実装**: `fetch-rclone.sh` が検証した**配布物のハッシュ**を `rclone.sha256` として同梱し、
診断画面はそれを「BUNDLED.md と照合する値」として表示する。
署名後の実体のハッシュは「参考値」として別に併記する（改ざん検知は codesign が担う）。

### M-14 — `operations/movefile` は移動先が存在しても**黙って上書きする**

**該当**: §8.6.3「取り下げ」

設計書は
「`gone/{key}` がすでに存在する状態で再実行すると `operations/movefile` が**失敗しうる**。
移動先に存在する場合は `gone/{key}.{unixtime}` にフォールバックする」
と規定していた。

実測では**失敗しない**。エラーも警告もなく上書きされる。
したがって危険は「二度押しで失敗する」ことではなく、
**二度押しすると先に取り下げた `gone/{key}` を失う**ことにある。想定と逆向きの事故。

**実装**: 移動前に `operations/stat` で存在を確かめ、あればタイムスタンプ付き key へ退避する。
フォールバック自体は設計どおりだが、**発動条件が「失敗したら」ではなく「事前に確かめて」**でなければならない。

## B. 実装で解消した未検証事項

### U-03 — `disable-library-validation` は**不要**（解決）

**該当**: §3.8 / G5-2 / §14.1 U-03

Hardened Runtime を有効にした Release ビルド（`flags=0x10002 adhoc,runtime`）で、
`com.apple.security.cs.disable-library-validation` を**付けずに**同梱 rclone を子プロセス実行できた。

理由: library validation は「**プロセスに読み込む dylib**」に掛かる制約であり、
別プロセスとして `exec` する実行ファイルには掛からない。
`go/linking: dynamic` は rclone 自身が system dylib を読むという話で、
それらは Apple 署名なので問題にならない。

**entitlement をプロジェクトから削除した。**

> **残る未検証**: この確認は **ad-hoc 署名**で行った。Developer ID 署名での再確認は G5-2 に残る。
> 機構上は同じ結論になるはずだが、証明書が無いため実測していない。

検証手段: `SkyFolder.app/Contents/MacOS/SkyFolder --selftest`
（Hardened Runtime は Xcode の実行やユニットテストのプロセスには掛からないため、この経路でしか確かめられない）

### G1-9 ⑧ — `deletefile` の冪等性を `type=local` で先取り

存在しないキーへの `operations/deletefile` は **HTTP 404 / `object not found`**。
設計書は「G1-9 で確認する」としていたが、local バックエンドで先に確認できた。
**「存在しない」を成功として扱う実装が必要**（接続テストの後片付けと `share-staging/` の掃除で重複実行が起こりうる）。

実 R2 での再確認は `--verify-r2` の `G1-9.8b` が担う。

## C. 設計書に無かった落とし穴

### M-15 — ImageIO のメタデータ除去は「入れない」だけでは効かない（SEC-08 が無言で壊れる）

**該当**: §7.4 / SEC-08（MUST）/ G-06

§7.4 は「プロパティ辞書から下記を**除去**する」と書いており、
素直に読むと「出力の properties にそのキーを載せなければ落ちる」と解釈できる。**それでは落ちない。**

`CGImageDestinationAddImageFromSource` の `properties` は
**元のメタデータとマージ**される。実装当初これで書いたところ、
**GPS も Exif も IPTC もそのまま出力に残った**（テストで検出）。

消すには Apple の規約どおり、キーに **`kCFNull` を明示**する必要がある。
ネストした辞書（TIFF の Make / Model / Software 等）も同じで、個々のキーに `kCFNull` を入れる。

これは **SEC-08（MUST）と G-08 の目的そのものが無言で無効化される**類の欠陥で、
「公開画像から GPS が消えている」ことを実際に検査するテストが無ければ気づけない。

**除去後に残るもの**（実測・識別情報ではない）:
`{Exif}` の `ColorSpace` / `PixelXDimension` / `PixelYDimension` は
ImageIO が JPEG 書き出し時に必ず付け直す。画像を見れば分かる構造的な値なので問題にならない。
したがって検査は「Exif 辞書が空か」ではなく「**識別情報のキーが残っているか**」で行う。

### M-16 — Orientation は消せない（DD-001 F-16 の懸念はこの経路では発生しない）

`CGImageDestinationAddImageFromSource` は **Orientation を無条件に引き継ぐ**。
`kCGImagePropertyOrientation` にも `{TIFF}.Orientation` にも `kCFNull` を明示しても消えない（実測）。

DD-001 F-16 は「Orientation を剥がすと公開画像が横倒しになる」を必須要件としていたが、
**この実装経路では剥がすこと自体ができない**。

実装には明示的な保持コードを残してあるが、mutation テストで
**消しても結果が変わらない（等価変異）**ことを確認済みで、コメントにもそう書いてある。
保証しているのはコードではなく**テストの表明**のほう。

### M-17 — read-only 拒否の errno は 3 種類。しかも**ログとは別物**

**該当**: §10.1 E-14 / M-02

**(1) クライアント側に返る errno は 3 種類**（設計書 M-02 は 2 つしか挙げていない）:

| 操作 | errno | 表示 |
|---|---|---|
| 新規ファイル作成 | 13 | `EACCES` Permission denied |
| **既存ファイルの上書き** | **72** | **`EBADRPC` RPC struct is bad** |
| 削除 | 5 | `EIO` Input/output error |
| リネーム | 5 | `EIO` Input/output error |
| ディレクトリ作成 | 13 | `EACCES` Permission denied |

**(2) ところが E-14 はログ監視で検知する設計であり、これらの errno はログに出ない。**

ログレベル INFO（§6.1 の既定）で出るのは次の 1 種類だけ:

```
2026/08/31 19:23:24 ERROR : nfs: Error Creating: Read only file system
```

設計書 M-02 の `permission denied` / `Input/output error` を検知語にすると**一度も発火しない**。
実装当初この 2 つを入れていたが、実測して `read only file system` の 1 語に置き換えた。

**(3) 削除とリネームは INFO でも DEBUG でも 1 行も出ない。**
したがって E-14 で案内できるのは**書込み試行のときだけ**である。
削除・リネームの拒否は OS のダイアログだけがユーザーに見えることになる
（§10.1 E-14 の「できないこと」に 1 項目追加が要る）。

### M-20 — Finder のメタデータ作成で E-14 が誤発火する

**該当**: §10.1 E-14 / DD-001 R-10 / R-G05

read-only マウントを Finder で開くだけで、macOS は `._*`（AppleDouble）や `.DS_Store` の
作成を試み、そのたびに拒否ログが出る（実測で `._existing.txt` を観測）。

E-14 の通知をそのまま出すと、**ユーザーが何もしていないのに警告が鳴り続ける**。
`._` / `.DS_Store` / `.Spotlight-V100` / `.Trashes` 等を通知対象から除外した。

なお §6.3 の `_filter` 除外はマウント先での**可視性**を制御するだけで、
Finder が作成を**試みる**こと自体は止められない。DD-001 R-10 が指摘していた現象そのもの。

### M-18 — パス表現の非対称（rclone は保存、OS は解決）

**該当**: §6.2 RULE / §8.4 手順 2

| 経路 | 返すパス |
|---|---|
| `mount/mount` と `mount/listmounts` | **渡した表現のまま**（`/var/folders/...`） |
| OS のマウント表（`getmntinfo` / `mount`） | **symlink を解決した**パス（`/private/var/folders/...`） |

macOS では `/var` → `/private/var`、`/tmp` → `/private/tmp` が symlink。
§8.4 手順 2 は「`listmounts` に含まれないが OS 側ではマウント状態」を判定するが、
**OS 側と比較するときだけは両側を解決してから突き合わせる**必要がある。
rclone の応答同士の比較には解決は要らない（表現が保存されるため）。

`statfs` は内部で解決するので `isMountPoint` は素朴な実装でも動くが、
`getmntinfo` の結果と設定値を直接比較する経路は壊れる。

### M-21 — 再起動時の rc 認証情報が「呼び出し側の書き方」に依存していた（SEC-G01）

**該当**: §6.1 / SEC-G01 / §8.2

SEC-G01 は「rc-user / rc-pass は**プロセス起動ごとの乱数**とする」と規定している。
実装当初、`RcdSupervisor.start(specFactory:)` は渡されたクロージャの戻り値をそのまま使っていた。

本番の呼び出し（`AppModel.activate`）はクロージャ内で `RcdLaunchSpec` を新規に組み立てるので、
再起動のたびに新しい乱数になる。**だが、それは呼び出し側の書き方に依存していた。**
spec を外に括り出す（自然な最適化に見える）だけで、
再起動後も**同じ rc-user / rc-pass が使い回される**ようになる。SEC-G01 が黙って破れる。

T-G15（rcd を kill → 自動再起動）のテストを書いたときに、まさにこの形で再現した。

**実装**: `RcdSupervisor.launch` が**起動のたびに必ず** `spec.regeneratingCredentials()` を適用する。
呼び出し側が何を返そうと認証情報は作り直される。
G-08 が「検知ではなく構造で消す」ことにしたのと同じ考え方で、
安全性を慣習ではなく型と制御フローで担保する。

単体テスト（`SEC-G01: spec を使い回しても rc 認証情報は作り直される`）と
統合テスト（T-G15 が古い認証情報で 401 になることを確認）の両方で固定した。

### M-22 — 「設定を保存しても効かない」経路と、ポーリングの積み上がり

**該当**: §6.2 注入経路表 / §8.1 / R-G08

自己レビューで見つけた、実装側の欠陥 2 件。設計書の記述の問題ではなく、
**§6.2 注入経路表が意味することを実装に落とし切れていなかった**もの。

**(1) 設定を保存しても rcd に反映されない**

リモート定義（accountId・認証情報）とグローバルオプション（transfers・チャンクサイズ）は
**環境変数でしか渡せない**ので、rcd のプロセス起動時にしか反映できない。
ところが `RcdSupervisor.start` は「すでに走っていれば何もせず既存の endpoint を返す」実装だった。

結果、設定画面で Account ID やトークンを変えて保存しても、
**rcd は古い環境変数のまま動き続ける**。ユーザーには「保存しました」と出るのに効かない。

**実装**: `RcdLaunchSpec.restartSignature`（rc-user / rc-pass を除いた環境変数と引数の指紋）を持ち、
変わったときだけ rcd を作り直す。
再起動は全マウントの解除を伴うので、`vfsOpt` で渡す設定（キャッシュ上限・書き戻し間隔・
ディレクトリキャッシュ）の変更では**再起動しない** — これらは `mount/mount` の呼び出しごとに渡るため。

あわせて、作り直す前に**未送信データを確認する**ようにした（R-G08 と同じ理由）。
これを省くと、設定を保存しただけでアプリ終了時と同じデータ喪失が起きる。

**(2) `activate` を呼ぶたびに `StatsPoller` と `LogWatcher` が積み上がる**

`activate` は起動時・設定保存時・プロファイル切替時に呼ばれるが、
古いポーラーと監視を止めずに新しいものを作っていた。
設定を 5 回保存すれば 5 本のポーリングループが同時に RC API を叩き続ける。

**実装**: `activate` の冒頭で必ず停止し、`restartPolling` で張り直す形に一本化した。
`handleRcdRestarted`（自動再起動の経路）も同じ関数を通す。

### M-23 — rclone の `mount/unmount` は生きた nfsmount で応答を返さない

**該当**: §6.2 / §8.3 / R-G08

実測（rclone v1.75.0 / macOS 26.6.2）:

| 操作 | 所要 |
|---|---|
| `mount/mount` | 0.036〜0.054 秒 |
| マウント上の read | 0.002 秒 |
| **`mount/unmount`** | **25 秒以上、応答なし**（rclone のログにも受信行以降が出ない） |
| **`mount/unmountall`** | **同上** |
| **`/sbin/umount`（OS 側）** | **0.017 秒で成功** |

読んだか読んでいないか、`vfsOpt` の内容、`_filter` の有無に関わらず再現する。

設計書は §6.2 でアンマウントを `mount/unmount`、§8.3 と R-G08 で `mount/unmountall` に依存しており、
**そのままだと「アンマウント」ボタンとアプリ終了が固まる**。
BUNDLED.md の冪等性表は `mount/unmountall`(2 回)→`{}` を記録しているが、
これは**マウントが 0 件のとき**の測定で、生きたマウントがある状態は測られていなかった。

**実装**: §8.6 の原則「操作ではなく**望む終了状態**に対して冪等にする」に従い、
RC API に期限（既定 10 秒 / 終了時 5 秒）を切って、そこへ到達していなければ
OS の `umount` で到達させる。順序は逆にしない（まず RC API を試すのは rclone 側の後始末を走らせるため）。
テスト実行時間は 400 秒 → 95 秒になった。

### M-25 — SIGTERM でマウントが自動解除されない（M-08 の前提が崩れている）

**該当**: §8.6.2 (b) / §8.4 手順 2 / M-08

設計書 M-08 は「マウント中の rcd に SIGTERM を送ると、プロセス終了と同時にマウントが自動的に解除された」
と記録し、§8.6.2 (b) の孤児回収はこれに依存している（だから RC API を呼ばなくてよい、という論理）。

実測では、**マウントを保持した rcd は SIGTERM で終わらず SIGKILL まで進み、マウントが残る**。
M-23 と同じ根（rclone のアンマウント経路が返らない）と見られる。

**帰結**: 孤児回収は SIGTERM だけでは完結しない。
**§8.4 手順 2 の例外規定（自分由来と断定できた残骸は `umount` してよい）が必須**になる
— 設計書はこれを「SIGKILL まで進んだ場合に備えた」補助的な位置づけにしていたが、実際は主経路である。

### M-26 — 元に無い辞書へ `kCFNull` を渡すと、消すどころかキーを生やす

**該当**: §7.4 / SEC-08

M-15（除去には `kCFNull` の明示が要る）の続き。**逆向きの落とし穴**がある。

元の画像が持っていない辞書（例: JPEG に `{PNG}`）を渡すと、
`kCFNull` を入れたキーが**空のエントリとして生成される**。
実測: JPEG を処理したあと、元に無かった `IPTC.CopyrightNotice` と `TIFF.ImageDescription` が
空の値で出現した。**除去のつもりの指定が、新しいメタデータを作る。**

あわせて分かったこと: **PNG のテキストチャンクは PNG / IPTC / TIFF の 3 箇所に写しが作られる。**
`Author` は `{PNG}` と `IPTC.Byline` に、`Copyright` は `{PNG}` と `IPTC.CopyrightNotice` と
`TIFF.Copyright` に現れ、**3 つとも潰さないと消えない**（どれか 1 つでも残すとそこから復元される）。
IPTC を辞書ごと `kCFNull` にしても消えず、個別キーで潰す必要がある。

**実装**: 「元にある辞書だけを対象にし、その中のキーを潰す」。
`CGImageDestinationAddImage`（source を経由しない書き出し）でも消えないことを確認しており、
ImageIO の経路ではこれが唯一の方法。

### M-24 — `kSecUseDataProtectionKeychain` は Team ID を要求する（SEC-G06(a) の現状）

**該当**: SEC-G06 (a)

独立レビューの指摘（正しい）: `kSecAttrAccessibleWhenUnlocked` は
**data protection keychain 専用の属性**で、`kSecUseDataProtectionKeychain: true` を付けないと
macOS は login.keychain へ書き、そちらは属性を**解釈しない**。
つまり「画面ロック中は読めない」は成立していなかった。

ただしその修正をそのまま入れると、**アプリが認証情報を保存できなくなる**。
実測: 署名済み `.app`（ad-hoc + Hardened Runtime）で `SecItemAdd` が
`errSecMissingEntitlement (-34018)` を返した。
data protection keychain は application-identifier entitlement を要求し、**Team ID が要る**。

**実装**: 使えるなら data protection、駄目なら legacy へ落ちる。
**落ちたことを `activeMode` で外から分かるようにし、診断画面に表示する**
— 黙って落ちると SEC-G06 (a) が満たされていない事実が見えなくなる。
Developer ID 署名では data protection が使えるはずなので、**G5-2 で再確認する**。

### M-19 — `Thread.sleep` を actor 内で回すと協調スレッドプールを塞ぐ

**該当**: §8.3 終了シーケンス / §8.6.2 (b)

孤児の回収と終了処理は「SIGTERM → 5 秒待って SIGKILL」だが、
この待機を `Thread.sleep` で書いて actor から呼ぶと、**協調スレッドプールのスレッドを最大 5 秒占有する**。
アプリ終了時（§8.3）に他の `Task`（未送信データの確認・ポーリングの停止）が進まなくなる。

**実装**: `ProcessInspector.terminateAsync` を用意し、非同期文脈からはそちらを使う。
同期版は残してあるが、docstring に「actor や Task の中から呼ぶな」と明記した。

## E. 実装上の判断（設計書が決めていなかったこと）

| 項目 | 判断 | 理由 |
|---|---|---|
| Kit の形態 | **静的ライブラリ** | フレームワークだと `.app` に入れ子バンドルが増え、G5 の署名・公証が複雑になる。実際 framework 版は `bundle format unrecognized` で署名に失敗した |
| プロジェクト生成 | **XcodeGen**（`project.yml` が唯一の正） | `.xcodeproj` を手で保守すると再現性が落ちる。§8.6 の冪等性と同じ考え方 |
| Swift 言語モード | **5**（コンパイラは 6.3） | 6 の厳格な並行性検査に合わせる作業が、この規模では価値に見合わない。actor と `@MainActor` は設計どおり使っている |
| A-03 角丸 | **macOS 11〜15 の従来方式**（1024 のキャンバスに 824 の角丸正方形・半径 185.4） | deployment target が macOS 14 のため。**設計書 A-03 の「現物にはすでに角丸が描かれている」は実測と食い違う** — 実描画領域 903×903 の四隅は 2px 程度の反エイリアスのみで、実質的に正方形だった。したがって「OS のマスクと二重になる」問題は起きない |
| A-04 / A-06 の 16pt 別版 | **コードで描画**（`make-assets.swift` 内の CoreGraphics） | 設計書は「自動生成できない人間の作業」としていたが、コードで定義すれば原本の差し替えに追随でき、§15.3 の再現性原則により適う。意匠は「塗りのフォルダから上向き矢印を抜く」— M-10 のとおり原本の線画は 16px で潰れる |
| `--selftest` / `--verify-r2` | **アプリに検証モードを持たせた** | Hardened Runtime 下の挙動（U-03）と実 R2 の通し確認（G1-9）は、テストバンドルからは確かめられない |
